# InspirationOS — Privacy & Security Model

This app processes private Instagram messages. These rules are binding for all
code and all future sessions; they take precedence over convenience.

## Never

- Ask for the Instagram password, automate Instagram login, bypass access
  controls, use cookies/headless browsers against Instagram, or handle
  CAPTCHAs.
- Commit raw Instagram exports, private messages, API keys, `.env` files,
  uploaded files, or generated user data to git.
- Log private message bodies. Redacted fields (never in logs, error strings,
  job payloads, or `ai_requests`): `text`, `share_text`, `adjacent_text`,
  `context_note`, `content_md`, and anything derived from message content.
- Send message content to any external service. AI providers receive only the
  minimal grounding context the user's generation request requires, and only
  when a real provider is explicitly configured.

## Git hygiene

- `.gitignore` covers `var/`, `private-data/`, `uploads/`, `exports/`, all
  ZIPs, all databases, `.env*` (except `.env.example`), logs, and temp files.
- **gitleaks** runs in pre-commit and CI; hooks are never bypassed with
  `--no-verify`.
- Test fixtures are synthetic only, generated by
  `backend/tests/fixture_builder.py`. The real export only ever lives under
  gitignored `var/`.

## Upload safety (ZIP handling)

- Size cap enforced before reading the body (default 2 GB, configurable).
- Streaming reads via `zipfile` — the archive is **never extracted wholesale**;
  only `message_*.json` (and `personal_information.json`) entries are read.
- Per-entry checks: resolved path must stay inside the target root
  (zip-slip); caps on entry count, total uncompressed size, and compression
  ratio (zip-bomb).
- Temp directories removed in `finally`; the original ZIP is stored via the
  Storage abstraction under gitignored `var/data/`, checksummed (SHA-256).

## Network policy

- **Import is fully offline.** No network request during upload/scan/extract.
- Enrichment requires: (1) the Settings toggle enabled after an explicit
  consent dialog stating that saved URLs will be sent over the network
  (consent timestamp stored), and (2) a per-item / per-selection / per-group /
  per-cluster "Enrich" action. There is no global crawl.
- Enrichment requests are anonymous GETs with an honest User-Agent, rate
  limited (token bucket), with timeouts, backoff, a circuit breaker, and a
  full audit trail in `enrichment_attempts`.

## Authentication & sessions

- Single user; password hashed with **argon2id**; `create-user` CLI seeds the
  account (no open registration).
- Server-side sessions in Redis (revocable), delivered via httpOnly, Secure,
  SameSite=Strict cookie. Frontend and API share an origin (Next.js proxy), so
  no CORS surface.
- Login rate limiting via Redis counters. CSRF posture: SameSite=Strict plus a
  required custom header on mutating requests.
- Every non-auth API route requires a session; this is verified by a test that
  sweeps all registered routes (M9).

## Logging & observability

- Structured logs pass through `services/privacy/log_filter.py`, which strips
  the redacted fields listed above; errors carry item/job IDs only.
- A test asserts that a full pipeline run over fixtures produces logs
  containing none of the fixture message strings.
- `ai_requests` stores tokens, cost, latency, status — never content.
- Optional Sentry (self-hosted-friendly) behind an env flag with scrubbing on.

## Career artifacts and export (M8)

- Career-artifact `content_md`/`payload` are generated text derived from a
  project's own already-generated, already-grounded fields (title, summary,
  tech stack, …) — never raw `share_text`/`adjacent_text`/`context_note`.
- The fabricated-claims guard (`services/generation/claims_guard.py`) flags
  suspicious performance-claim language for the user's attention; it never
  blocks generation and never sends anything anywhere — it's a local regex
  check over already-generated text.
- Export files (Markdown/JSON bundles) are written through the existing
  `Storage` abstraction under gitignored `var/data/exports/`, the same as
  every other stored artifact — no new exposure surface, no new network
  calls; the download endpoint streams straight from that storage key.

## Data deletion (three scopes, each with typed confirmation)

1. **Raw import data** — deletes the stored ZIP, conversations, and messages.
   The user chooses whether derived items survive (source references nulled)
   or cascade-delete.
2. **Project deletion** — project + milestones + artifacts (+ exports, whose
   FK cascades on project deletion; the underlying export file is not
   auto-deleted from storage — cleanup of orphaned export files lands with
   M9's complete-wipe filesystem check, same as other stored artifacts).
3. **Complete wipe** — every table except `users`, plus all stored files; runs
   as a job and produces a verification report (row counts before/after,
   filesystem check).

## Transport & production posture

- Prod: only Caddy is exposed (443/80→redirect); backend, worker, Postgres,
  and Redis live on an internal Docker network. Automatic TLS via Let's
  Encrypt.
- Secrets are environment variables on the VPS — never in git, images, or
  build args. `.env.example` documents every variable with placeholders.
- Backups (nightly `pg_dump` + `var/data` archive) are private data too:
  stored with restricted permissions, covered by the same deletion promises.
